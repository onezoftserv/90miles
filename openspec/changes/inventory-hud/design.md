# Design

## Context

See proposal.md "Why". C, E and Q were measured on 06e9f2c by running the game shell headless; the branch was then fast-forwarded to main (8d3c4ca), and everything below was re-read there. Main added creatures-ai (archived) and coop-reconnect (active), and neither changes what C, E or Q do. Apply started on main at 27bebe8, which adds crossing-late-join (`CrossingSnapshot`, `Crossing.restore`, `IslandRoutes` progress for joiners, `GameShell._on_progress_received`); it touches none of the HUD, input, interaction or inventory code below.

- `RunHud` (`game/scenes/ui/run_hud.gd/.tscn`) is a CanvasLayer (layer 3) added to `GameShell`'s root, while the world draws in `WorldView/Viewport`, a 640×360 SubViewport inside a SubViewportContainer at 0,0. It binds `MetersHud` to the local player in two places: `_follow(local_peer)`, and `_on_player_rebound` (coop-reconnect), which re-binds `meters` when a rejoined client takes back its body. The day phase sits top-centre, the teammate list top-right, every panel uses `theme_type_variation = HudPanel` (a dark StyleBoxFlat at 75 %) and `mouse_filter = 2`. The bottom band is free. `QuickChatWheel` is the pattern for an input-driven HUD piece: it polls an action in `_process` and ignores input while a `LineEdit` has focus.
- `PlayerInput` polls `Input.is_action_pressed` for move, run, crouch and interact and writes a `MoveIntent` into the body each physics frame. Marking an event handled does not stop it; only solo pause, which freezes the tree, keeps it from reaching the body.
- Interactions run only where the world is authoritative: `PlayerBody.advance(delta, with_interaction)` gets `false` on a predicting client. `InteractionPicker.pick` is a pure static function (nearest enabled within `REACH_PX` 16, `usable_by`, not the player's own). `PlayerBody._update_interaction` picks only on a fresh press; `InteractionHold` then keeps that target until release, until it is disabled, or until the player is beyond `REACH_PX + REACH_SLACK_PX` (18 px).
- Interactables: `world_item.tscn`, `palm.tscn`, `build_site.tscn`, `fire.tscn`, `rain_catcher.tscn`, `raft.tscn` and, new on main, `creature.tscn` each give a child node the plain `interactable.gd`; only `DragHandle` and `RescuePoint` extend `Interactable`. `Creature._ready` enables its Interactable (hold 0) when its data has an INTERACT counter: the seagull (`seagull.tres`, trigger 6, radius 2 tiles, `name_es` "Gaviota"), two of which nest at `nest_palms [4, 5]` on the sandbar with `SandbarIsland.with_creatures = true` by default. `Fire` keeps `interactable.enabled = lit`; `Palm` and `RainCatcher` never touch `enabled`, so a bare palm and an empty catcher stay pickable everywhere, solo included (their handlers just return).
- `Inventory` lives on the host; `PlayerNet.net_inventory` replicates `Inventory.to_net()` (`[id, count, uses_left]` per slot, slot 0 first) and clients call `from_net`, which emits `changed`. Meters, movement state and stealth state already replicate. `Inventory.held_food()` (creatures-ai) is the first FOOD slot; `swoop_steal.gd` takes it from a player within a gull's sight (8 tiles) of the nests.
- `CoopSession.use_item(slot, use_index, target_peer)`, `craft(recipe_id, station_path)` and `deposit(site_path)` are host-authoritative RPCs, rate limited per client (`PeerLimits.allow_action`), and return nothing. `_acting_body` refuses a dead or downed player, a last stand unless allowed, and a player who `_has_left` by a route. `IslandRoutes._depart` fills `departed` on every peer when a route starts, while `left_island` is set only by `ArrivalStub.hold` after `Crossing.ended`: so for the whole 60-120 s crossing the host refuses every use from a rider. `use_for` lets a solo last stand act only with a reviving use and checks the target's reach. `ItemUser.use` returns a bool and checks, in order: slot, item and use exist; `subject != actor and not can_target_others`; `subject.meters.dead`; a reviving use on a subject who is neither downed nor in a last stand; the conditions.
- Peers and names: a reclaimed body keeps the node name of the peer it first spawned under, so `CoopSession.peer_of(body)` is the only way to a body's peer (`raft.gd`, `rescue_point.gd` and `crossing.gd` use it).
- Spawners: `CoopSession._ready` sets `entity_spawner.spawn_function = _spawn_entity`, which builds only creatures (`catalog.has_entry(&"creatures", id)`, else null). A MultiplayerSpawner has one spawn function, and it replays the arguments given to `spawn()` to a later joiner, not the node's current state.
- `Crafter.start` accepts only `station == WORKBENCH`, `output_kind == ITEM`, not `build_site`, and checks `station is Workbench`; `Crafter.place_site` exists but nothing in a run calls it. All three recipes (`fire`, `rain_catcher`, `raft`) are `build_site` with `station = NONE`, and `RecipeData.placement_terrain` ("empty means any land") is read by nothing. The raft's site is placed by the level (`SandbarIsland._place_raft_site`, `synced = true`).
- `BuildSite`: `receive_state(deposits, progress, is_built)` loops only `recipe.inputs`; `deposit()` calls `_push_state()` after the item loop and before the tag loop, and only when items moved; `tags_deposited` is never sent; a later joiner gets nothing until the next push (the raft site has the same gap today). `fire.tres` has `input_tags {TINDER: 1}` and `fast_tool = LIGHT_FIRE`, so a client's copy of a fire site never has its inputs complete. `_complete()` always loads the structure scene, instantiates it, adds it to the parent and calls `on_built`, on whichever peer runs it; `Fire.on_built` lights and applies `MoraleEvent.FIRE_LIT` to nearby players. No `build_sites` group exists.
- `Workbench` is a bare `Node2D`; `workbench.tscn` holds only that script. It is made with `Workbench.new()` in `SandbarIsland.furnish` (as `HutWorkbench` under the session, on every peer), `movement_playground.gd` and five crafting tests.
- `GameShell._check_run_over` shows the summary through `_show` and leaves the HUD up; on host lost, `CoopSession._on_server_disconnected` frees the bodies and `_end_run` frees the HUD a frame later (`call_deferred`).
- The theme's `Label` is cream with a 1 px shadow; `game_theme.tres` defines no outline. `NameTag` sits at (0, −22) with its label from y −31, and shows over a teammate whenever health is below full, so always over a downed one.
- Items have no sprites yet, names are Spanish-first (`ContentData.name_es`), and `ItemUseData.action` gives each use's verb. Free gamepad buttons: X (2), Y (3), Back (4), the stick clicks (7, 8), the D-pad (11-14) and the triggers; A interact, B crouch, LB run, RB quick chat, Start pause.
- The content validator treats every folder of `game/resources/` as a content type (crossing design), so a tuning-like data file goes at the root of `resources/`.

## Goals / Non-Goals

**Goals:**
- One code path for solo, host and client: every HUD piece reads the local `PlayerBody` and its mirrored state, and every world change goes through the existing session RPCs.
- The HUD never trusts itself: it pre-checks to explain, the host decides.
- Every word on screen comes from data (`hud_text.tres` and content names).

**Non-Goals:**
- A full inventory window, drag-and-drop, splitting stacks, dropping or giving items, equipment slots.
- A placement mode that puts a build site anywhere; crafting at a fire; cooking.
- A new host-to-client refusal message (see D6).
- Syncing palm coconut counts, rain-catcher cups or a fire's burn-out to clients (existing gaps, listed under Risks).
- Rebinding, PlayStation glyphs, item and character art.

## Decisions

**D1. HUD pieces and where they draw.** `RunHud` gains, in its CanvasLayer: `InventoryStrip` (bottom band), `CraftList` (left, above the strip), `HudNotice` (the 2 s refusal line), `InteractPrompt` and `BodyMarks` (the hidden marks). All bind to the local body through one `RunHud._bind_local(player)` called from `_follow` for the local peer and from `_on_player_rebound`, next to `meters.bind`, so a rejoined client gets them on its reclaimed body. Each piece reads the body through `is_instance_valid` and hides when it is gone (host lost frees bodies a frame before the HUD). The prompt and the marks are placed each frame from `target.get_global_transform_with_canvas().origin`, the point in the world SubViewport's own pixels (camera applied), mapped through `WorldView.get_global_transform()` into HUD coordinates (identity today: the container sits at 0,0 at 640×360) and rounded to whole pixels. Drawing them in the HUD layer keeps them crisp, above every world node, and out of the Suave Scale2x filter and the night tint, which apply to the world only. *Alternative:* a prompt `Node2D` in the world under the target: rejected, it would be filtered and tinted with the world and drawn under other world nodes.

**D2. Input routing.** New actions in `project.godot` by physical keycode: `use_item` (F, joypad 2), `slot_1`-`slot_12` (1-9, 0, minus, equal), `slot_next` / `slot_prev` (mouse wheel down/up, joypad 14/13), `list_up` / `list_down` (arrow up/down, joypad 11/12). Confirm in the list is `interact` (E, A) or a click; Enter is not used because Alt+Enter toggles fullscreen. `PlayerInput.build_intent` sets `interact_held = false` while the body's `hud_holds_interact` flag is true; `RunHud` sets it while the list is open and keeps it until interact is released after the list closes, so the host never sees an interact press meant for the list and the E that chooses a fire does not also deposit into the site that appears under the player. The press that opens the list does reach the host as an ordinary interact on the bench's Interactable and does nothing there. While the list is open, `use_item` is ignored: no hold starts and nothing is sent. `CraftList` takes `pause` in `_input` (before `PauseMenu._unhandled_input`) and marks it handled, so Esc closes the list first, in solo and in co-op (coop-networking "Pause" delta). The wheel is read in `RunHud._input`, before the GUI, and routed to the list while it is open and to the strip otherwise, so a slot that takes clicks (`MOUSE_FILTER_STOP`) never swallows it; slot keys and the D-pad are read in `_unhandled_input`; `use_item` is polled in `_process` for the hold, like `QuickChatWheel`. Slots and list rows take clicks but never focus (`focus_mode = FOCUS_NONE`), so Godot's `ui_*` focus navigation never steals the D-pad or A. The `LineEdit` focus guard is copied from `QuickChatWheel._process`. Screens: `GameShell` calls `hud.set_screen_shown(true)` when it shows the run summary (`_check_run_over`, which leaves the HUD up) or the host-lost screen (`_on_host_lost`, a frame before `_end_run` frees the HUD); while that is set or the pause menu is visible, every HUD piece ignores input and sends nothing. A test walks `InputMap` and fails on any event bound to two actions. *Alternative:* confirm the list with F: rejected, E opens the list so E choosing in it is what a player tries first, and F already means "use what I hold".

**D3. The local candidate and the hold ring.** With no interact held, the HUD calls `InteractionPicker.pick(body.global_position, interactables, body)` each frame, the same pure function the host runs, so the prompt names what the host's press will reach. On a fresh local interact press a `PressTimer` (RefCounted) locks that candidate, as `InteractionHold` does: it counts `delta` while interact is held, keeps the target even when another comes nearer, and resets on release, when the target is disabled or freed, or when the player is beyond `REACH_PX + REACH_SLACK_PX`; the prompt shows the locked target until then, and only re-picks with no press held. It never calls `use`. It ticks in `_physics_process`, so on the host and in solo it runs on the same frames as `InteractionHold`; on a client it runs ahead of the host by the latency. *Alternative:* read `body.interaction_hold` on the host and replicate progress to clients: rejected, it adds a synced field per player for a cosmetic ring and still lags on clients.

**D4. Prompt text is data.** `Interactable` gains `@export var prompt_id: StringName` and `@export var hides_contents: bool`, set on the Interactable node in each scene (or by the owner in code for state-dependent kinds, such as the crossing lashing's tie/untie), and a virtual `prompt_target(by: Node, locale: String) -> String`. Its default asks the Interactable's parent, the content owner (`get_parent().has_method(&"prompt_target")`), and returns "" otherwise; `DragHandle` and `RescuePoint`, which are Interactables, override it. Owners that name content define `prompt_target` once per kind, never per item: `WorldItem` (its item's name), `BuildSite` (its recipe's name), `RainCatcher` (the name of `produces_item_id`), `Creature` (its `CreatureData` name), and `DragHandle` and the crossing's pull point (`session.player_name(session.peer_of(body))`, never the node name). An Interactable with an empty `prompt_id` shows the key alone ("[E]"), and a test fails on any scene under `game/scenes/` whose Interactable has none. `HudText` (`game/scripts/ui/hud_text.gd`, data in `game/resources/hud_text.tres`) holds, Spanish and English: prompt verbs and default labels by prompt id, use verbs by `ItemUseData.UseAction`, tag names by `ItemTag`, tool phrases by `Capability` ("abrir el coco", "prender candela") with the list's "Con qué %s" and "Más rápido: %s", refusal lines by key, the weight label, "Falta:" and the joypad button labels. **D5. Using an item.** Two layers, each shared by the host and the HUD. `ItemUser.check(actor, slot, use_index, target) -> Reason` is extracted from `ItemUser.use` with exactly its checks in its order (`use` calls it first, so host behaviour is unchanged): `EMPTY` (no slot, no item), `NO_USE` (no such use), `NOT_TARGETABLE` (another subject and not `can_target_others`), `TARGET_DEAD`, `NOT_DOWNED_TARGET` and `CONDITION` with the first failing condition. The actor's own state is `use_for`'s, not `use`'s: `UsePlan.actor_reason(player, departed, slot, use_index, target)` returns `DOWN` (dead, downed, or a last stand that is not reviving themself), `AT_SEA` (departed on a route, see D11) or `OUT_OF_REACH` (target beyond `REACH_PX + REACH_SLACK_PX`), and `CoopSession.use_for` calls the same function before `ItemUser.use`. The rate limit stays host-only. A pure `UsePlan.choose(body, slot, players)` picks the use per spec "Which use the button picks" from the item's data (a `REVIVE` effect; `can_target_others`), skipping dead teammates, and resolves the target's peer with `session.peer_of`. The HUD runs both layers on the state this peer mirrors (its inventory from `from_net`, replicated meters and climate, `IslandRoutes.departed`), shows the reason's line (`NOT_TARGETABLE` and `TARGET_DEAD` share the generic "Ahora no se puede."), and only on `OK` starts the hold for the use's `time_s`; at completion it calls `session.use_item(slot, use_index, target_peer)`. "Down" in the HUD means `meters.downed`, and a last stand is `meters.last_stand`: `PlayerBody._on_last_stand_changed` sets `body.downed` during a solo last stand too, so a HUD that read `body.downed` would block the last-stand drink.

**D6. No refusal reply from the host.** A mismatch between the client's view and the host's (latency, or host-only state such as a condition kind clients cannot see) makes the host refuse silently, as today. *Alternative:* an authority-only `action_refused(reason)` sent with `rpc_id` to the requesting peer, checked against the host's id like `show_quick_chat`: kept as a follow-up if playtests show silent refusals; it adds a new message type for a case an honest client rarely hits once D11 covers the crossing.

**D7. The workbench list.** `Workbench._init` adds its own `Interactable` child (`hold_time_s = 0`, `prompt_id = &"workbench"`), as `Crossing` adds its `RescuePoint`s, so every `Workbench.new()` call site (the sandbar, the movement playground, the crafting tests) gets one with no change; `workbench.tscn` stays the bare script. Its `interacted` signal has no listener, so the host's copy of the press changes nothing. The HUD opens the list on a fresh local press whose locked candidate's parent is a `Workbench`. Rows: `GameState.content` recipes with `availability == KNOWN` and either (`station == WORKBENCH`, `output_kind == ITEM`, not `build_site`) or (`build_site`, `output_kind == STRUCTURE`); vessels stay with their island's routes. Sorted by `name_es` with a `String` comparator (CLAUDE.md: `Array[StringName].sort()` does not sort by text). An input, tag or required tool is missing while the carried count is below the needed one; dimming a workbench row uses `Crafter.can_craft`, which only reads the inventory and so is safe on a client's mirror. A recipe's `fast_tool` is listed as "Más rápido: <phrase>" and never dimmed. A refused choice (dimmed row, or an unfinished site of that recipe in `build_sites`) shows its line and keeps the list open. The station path is `session.get_path_to(bench)`. *Alternative:* add a workbench-only "build" recipe list in new data: rejected, the recipe files already say which are build sites.

**D8. Placing a site and seeing it everywhere.** `CoopSession.craft_for` keeps `Crafter.start` for workbench recipes. For a build-site structure recipe it requires the station to be a `Workbench` (`station is Workbench`, as `Crafter.start` checks) within `REACH_PX + REACH_SLACK_PX` of the sender's own player, no unfinished site of that recipe in the new `build_sites` group (every `BuildSite` joins it in `_enter_tree`, the level's raft site included), and the free cell nearest the player within 1 tile whose terrain is in `recipe.placement_terrain`, or any land when it is empty (now read for the first time): not the bench's cell, no structure or site within half a tile. `_spawn_entity` keeps the one spawn function and dispatches on a `kind` key in the payload: absent or `creature` builds a creature as today; `site` builds a `BuildSite` (payload: name `Site<serial>`, recipe id, position); `structure` builds the structure scene (payload: name, recipe id, position, and for a fire whether it is lit). Each kind is checked like `_spawn_pickup`: the kind in that fixed set, the recipe in the content's `recipes` as a build-site structure, a finite position, a safe plain name. Spawned sites set `synced = true`, `spawned = true` and the session's `climate`, and so does each structure, as `Crafter.place_site` does, or a spawned rain catcher never sees the squall. Site state: `receive_state` gains the tag deposits (`receive_state(deposits, tag_deposits, progress, is_built)`, each clamped to the recipe), and `deposit()` pushes once after both loops when anything moved. Because the spawner replays only the spawn payload to a joiner, a client's synced site asks for the live state when it is ready (`request_state`, any_peer, limited by the sender's `PeerLimits`; the host answers that peer alone with `receive_state.rpc_id`); the level's raft site gets the same, which closes its joiner gap too. Completion: a spawned site's `_complete` only marks it built and disables its Interactable; on the host it then asks the session once to spawn the structure and frees itself (the spawner removes it on every peer). No peer instantiates the structure locally, and `on_built`, with its morale event, runs on the host alone; a client's fire only shows itself lit. A client's `receive_state(..., is_built = true)` for a spawned site only marks it built. The level-placed raft site keeps its present completion path. *Alternative:* a second MultiplayerSpawner for sites and structures: rejected, the dispatch is one more key in a payload already checked, and the entities node stays the one place world things spawn. *Alternative:* deposits and progress in the spawn payload: rejected, a joiner would get the state at placement time.

**D9. Crouch cue and hidden mark.** A small `BodyLook` node on the player reads `movement_state` each frame: crouch scales the sprite to 10/16 in y with an offset that keeps its bottom edge. The hidden mark is not a world node: `BodyMarks` in the HUD draws one per player whose `stealth_state` is hidden, placed as in D1, so neither the Noche tint (`Color(0.35, 0.4, 0.65)` from `day_cycle.tres`) nor Suave touches it. Clients already receive both states, and a client's own player uses its predicted state, so the cue is immediate for the player and 100 ms behind for teammates. Submerged (diving) gets no mark: the dive has its own look later with the swim art.

**D10. Key labels and the last device.** `InputLabels.label_for(action, device)` reads `InputMap.action_get_events`: for keys, the layout's glyph for the physical keycode (`DisplayServer.keyboard_get_keycode_from_physical`), so a Spanish keyboard shows its own key on slots 11 and 12; for joypad buttons, the label from `hud_text.tres` (Xbox names). `RunHud._input` switches the last device to gamepad on a joypad button press, or on joypad motion that presses an action past that action's deadzone, so stick drift and trigger noise do not flip it; a key press or a mouse button switches it back. Slot keys are drawn in each slot's top-left corner while the device is the keyboard.

**D11. Items on a crossing (owner confirmed (b), refuse at sea, 2026-11-08).** The host refuses every use from a rider for the whole crossing (`_acting_body` checks `_has_left`), and GAME_DESIGN.md §8 does not say whether items can be used at sea. This change does not pick silently: it mirrors today's host rule as the provisional default, and the owner decides. Default (b): `UsePlan.actor_reason` returns `AT_SEA` while `IslandRoutes.departed` holds the local peer; the strip stays, the selected item's line drops "[F]", and F shows "En plena travesía no se puede." Nothing on the host changes. The other option (a): riders may use items at sea; it needs a crafting-inventory or crossing delta that lets `_acting_body` accept a rider in a live crossing, and the strip keeps "[F]". Either way task 4.8 adds a solo crossing test with a rain cup.

## Risks / Trade-offs

- [The client's pre-check sees a stale or partial view] → The same `ItemUser.check`, `UsePlan.actor_reason` and `Crafter.can_craft` run on host and client; reasons are only drawn for state clients mirror; the host refuses silently otherwise (D6). Playtest; add the refusal reply if it bites.
- [The client's ring fills before the host applies the hold] → Documented in the spec; the ring stays full until release, and the strip and meters change when the host's state arrives.
- [Prompts on things that do nothing] → A bare palm reads "Trepar Mata de coco" and an empty rain catcher "Tomar Vaso de agua de lluvia" everywhere, solo and the host included, because `Palm` and `RainCatcher` keep their Interactables enabled; the hold then gives and costs nothing. On a client, "Apagar Fogata" can also show over a fire that burnt out on the host. Disabling them at 0 and syncing palm counts, cups and burn-out stay follow-ups (sandbar-island "palm counts synced to clients", the crossing follow-up list).
- [A gull is nearer than the palm] → At a nest palm the picker may choose the gull, so the prompt reads "Espantar Gaviota"; that is what the host's press would do, so the prompt stays honest.
- [A modified client can skip a use's `time_s`] → crafting-inventory already gives the time to the caller; the per-client action limit bounds abuse. Host-timed uses are a later change if needed.
- [Sites only at the bench cluster fires in the hut] → Fine for the sandbar, where the hut is the camp; a placement mode is a follow-up.
- [Two site paths (level-placed and spawned)] → The raft's completion path is untouched; tests cover a spawned fire on host, client and a late joiner, and a single fire after completion.
- [The spawn function now serves two owners] → creatures-ai's creature branch keeps its checks; a test spawns a creature, a site and a structure through `_spawn_entity` and a payload with an unknown kind returns null.
- [The 13th (Experiencia) slot has no number key] → Reachable with the wheel, the D-pad and a click.
- [Wheels and touchpads send bursts] → One step per wheel event; tune if playtests find it too fast.
- [ui-shell's "HUD layout" still says the bottom band and the centre stay clear] → This change's `specs/ui-shell/spec.md` modifies it and adds "Inventory band and world marks"; archive refuses it until ui-shell is archived, so ui-shell archives first (tasks "Workflow").
- [Typed arrays of our own classes leak at exit] (crossing) → Use `Array[RefCounted]` or `Array[Node]` where needed.

## Changes from the build plan

- **Prompt ids arrive with the HUD text (tasks 1.3-1.4, from 5.3).** 1.3's scene walk needs `Interactable.prompt_id`, which 5.3 adds.
